AI preparation, human authority

The Bridge reads translationCore project state and project-aware Translation Helps, prepares alignment/TN/TW/QA work with AI, gathers evidence, and lets the human reviewer make the authoritative decision.

Never automatic: Scripture changes, approved alignment, TN/TW completion, terminology rules and final approval require an explicit human action.

Start

  1. Load the translationCore data folder.
  2. Select project/chapter/verse.
  3. Open Settings & Log, enter reviewer/API settings and test the API.
  4. Use Dashboard → Prepare Changed / Untouched to avoid rechecking current cached work.

Reviewer speed

Use F5 for Full Verse Review, F8 for Next Priority, Ctrl+Enter to Accept, Ctrl+Shift+D for Needs Discussion, Ctrl+Shift+R to Reject AI, and Ctrl+Shift+Right for the next verse. Optional Auto-advance moves directly to the next priority item after a decision.

Changed-only chapter review and the exception-first queue keep already-current work out of the review path.

AI precision / false-positive reduction

AI findings pass through a deterministic evidence/confidence gate before entering the main queue. Very low-confidence and duplicate findings are suppressed from the priority queue, while insufficiently supported Critical/High findings are downgraded. Uncertain TN/TW conclusions become review rather than an overconfident pass/problem.

Suppressed items are not destroyed: they remain inside the saved AI review as an audit trail. Use Low-confidence Audit in AI Final Review to inspect them.

Language-aware plugin architecture

The Bridge detects the target language primarily from project/manifest metadata, with Unicode script evidence as a fallback. Source language is detected from source tokens (Hebrew/Greek) with canon fallback. Bundled target plugins include Tamil, Hindi, Malayalam, Telugu, Kannada, Gujarati, Bengali and Punjabi plus a generic safe plugin.

The active plugin changes labels, fonts, QA categories and AI guidance. Tamil-specific Sandhi/word-joining checks are therefore used for Tamil projects and are not blindly applied to other languages.

Paratext-compatible reviewer notes

When a reviewer enters a comment for an AI/tC decision, the Bridge can mirror it into a Paratext Notes 1.1-compatible XML exchange file under .apps/translationCoreAI/paratextNotes/. Production → Export Paratext Notes… copies the current book notes XML to a location you choose.

This release creates compatible exchange XML; it does not claim direct authenticated posting to a Paratext server.

Responsive desktop UI

v0.7.0 supports a minimum window of 760×560. The sidebar hides on smaller widths, controls reflow into rows, explanatory header labels collapse, and status/progress/token/cost indicators remain visible. At compact widths source/target token lists remain side-by-side and Current Alignment Groups moves into a mirrored scrollable viewer below them, so groups never disappear. Long token/group/proposal/evidence content has horizontal scrolling.

The Alignment toolbar is outside the AI Proposal split pane, so dragging the proposal sash cannot hide action buttons. Important controls also provide delayed hover tooltips. The AI Final Review keeps Severity + Tool Viewer and Result + Evidence as aligned panes with fixed decision actions below them.

Recommended workflow

Open project → scan state → AI prepare changed work → exception-first queue
→ human Accept / Edit / Discuss / Reject → approved tC state
→ changed dependencies become stale → AI reprepare → human final approval

Alignment

Connect source topWords to existing target-language bottomWords manually or use AI Suggest. One-to-one, one-to-many, many-to-one and many-to-many are supported. AI can only reference supplied token IDs. Apply AI Proposal changes the in-memory editor; Save Approved Alignment is the human write action and synchronizes tC Word Alignment completion.

The AI Proposal uses role colors: source language purple, target language teal/green, English rationale slate/gray, and confidence green/amber/red.

AI Final Review

AI resolves Hebrew morphology, current alignment, Translation Notes, relevant Translation Academy method, Translation Words, TW Links, prior tC decisions, human terminology rules and secondary reference evidence. It proposes exact target-language selections, verdict, severity, correction suggestion, confidence and evidence.

  • Accept synchronizes the human-approved TN/TW selection into native tC checkData/index.
  • Edit Selection uses only real current target-language tokens.
  • Needs Discussion records companion decision/audit and synchronizes a native tC comment.
  • Reject AI records the rejection; an optional reviewer reason can be synchronized as a tC comment.
  • Edit Scripture… opens the human correction workspace.

Quality Queue

Deterministic and AI findings are severity-ranked. Each finding can be accepted, discussed, rejected or used to open the Scripture editor. Final approval is role-gated and warns about stale AI review or unresolved Critical/High findings.

Human Scripture edits are transactional, reconciled with existing alignment, invalidate Word Alignment, mark affected checks/reviews stale and preserve append-only audit history.

Terminology / Translation Words analytics

The Terminology workspace combines trusted human rules with book-wide TW analytics: concept occurrence count, checked count, distinct target-language renderings, approved/allowed/rejected classification and unexplained occurrences. Human rules outrank AI preference and may allow contextual alternatives.

Specialized Psalms QA

The Psalms module surfaces review candidates from Hebrew cantillation/colon clues, repeated lemmas, contrast/negation patterns, alignment density and Tamil structural cues. These are evidence prompts—not automatic scholarly claims about the final poetic structure.

Production workspace

Crash recovery

Multi-file mutations start with a durable transaction journal and backup. If a prior session ended while a transaction was prepared/writing, v0.7.0 detects it and can roll it back conservatively.

Git

View repository status/diff and create explicit human checkpoints. AI-prepared work is not automatically committed as approved Scripture.

Team

Roles: translator, reviewer, consultant, administrator. Assign the current verse to a team member. Final verse approval follows the configured role policy.

Performance/plugins/metrics

The app materializes verse check indexes for fast repeated lookup, includes Tamil/Hindi/Malayalam/Telugu/Kannada/Gujarati/Bengali/Punjabi/generic target plugins plus Hebrew/Greek source descriptors, and tracks observed AI preparation, human decisions, cache skips, tokens and estimated cost.

Security and privacy

  • Remembered API keys use Windows DPAPI; plaintext keys are not persisted in settings.
  • Logs redact API-key/Bearer patterns.
  • Production → Security Scan checks the package tree for likely embedded secrets.
  • AI requests use store:false.
  • What Was Sent to AI? displays the last request privacy manifest: field names and data classes, not unrelated project files.
  • Knowledge Base evidence records project/resource version and SHA-256 provenance.

Publication QA reports

Production → Export QA Report creates print-friendly HTML, JSON, QA CSV, exception CSV, terminology CSV and discussion JSON. The report includes a deterministic publication-readiness gate, Knowledge Base provenance and quality/cost metrics. The gate is advisory; final publication approval remains human/organizational.

Windows packaging

Run build_windows_exe.bat for the icon-bearing PyInstaller package. GitHub Actions can build/test on Python 3.11 and 3.12 and create an Inno Setup installer. Before distribution, complete docs/WINDOWS_CERTIFICATION_CHECKLIST.md on the exact packaged EXE/installer.

A Linux source regression cannot prove Windows runtime behavior. The Windows checklist is intentionally a separate release gate.

Windows source setup & certification

v0.7.0 includes the Pillow-free source bootstrap and additionally hardens Tk/Tcl shutdown plus isolates every real-Tk Windows certification test into a fresh Python process. Source mode now uses Tk native image loading and creates an isolated local .venv automatically.

Use run_windows.bat to launch. Use test_windows.bat for portable tests; provide the translationCore data folder when prompted to run real-data tests. For an explicit full real-backend gate, run certify_windows.bat "C:\path\to\translationCore". The selected folder must contain projects and resources. If Python behaves unexpectedly, run diagnose_windows.bat.

Production testing

The v0.7.0 source/application gate contains 99 production tests: 75 core/data tests plus 24 real-Tk GUI tests isolated into fresh processes for Windows certification. The suite covers real Genesis/Ruth/Psalms/Obadiah-capable project data, destructive writes on disposable copies, rollback/crash recovery, native comments, KB provenance, terminology analytics, Psalms QA, reporting, Git, routing/cost, security, responsive UI breakpoints and a synthetic 66-book/~31k-verse scale fixture. Automated fixture mode is explicitly read-only against the original extracted backend.

Windows binary certification remains a separate gate because the exact EXE/installer must be executed on Windows.
